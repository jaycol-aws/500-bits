500 Bits to Impact
The Life of a Single Observation

Every dashboard, every alert, every 3 a.m. page begins as a few hundred bits of truth emitted by your code. In this hands-on hour we follow one OpenTelemetry metric observation end to end — from the moment an app records it, through its OTLP journey into the new CloudWatch OTel metric store, querying it back with PromQL, and — when an incident strikes — handing it to the Amazon DevOps Agent to pinpoint root cause.

Mostly live terminal + console. The deck is just the map.

Speaker (0:00–0:30): Open cold. Read the first sentence of the abstract, then set the contract: "I'll spend most of this hour in a terminal — the deck is just the map." Don't over-introduce yourself; get to the hook fast. Frame the through-line: we follow one metric observation from the code that emits it all the way to a root-cause investigation.
Act 0 · Framing

How big is one observation?

  • Bare (timestamp, value) ≈ 128 bits
    two 64-bit numbers, no context
  • Self-describing point ≈ 1,000–1,600 bits
    name, resource attrs, labels, units, encoding
  • Batched on the wire ≈ 120–160 bits
    shared context amortized across the batch
~500
bits — an honest, rounded hook
between the batched floor and the standalone ceiling
Speaker (~4m): Walk the three numbers top to bottom. Pause on the jump from 128 bits to ~1.6 Kbits — that's the price of being self-describing, which is the whole point of OTel. Then show how batching amortizes it back down. Land "~500" as an honest, rounded hook, not a spec constant — the candor buys you credibility for the rest of the hour. Transition: "so let's watch one of these get born."

Act 4 · Incident (the payoff)

Break it on purpose

# healthy: error ratio returns no series (Query Studio, PromQL) sum(rate({__name__="checkout_requests_total", outcome="error"}[1m])) / sum(rate({__name__="checkout_requests_total"}[1m])) # inject the incident ./inject-fault.sh error 0.6 # ~1–2 min later: ratio > 0.2 → ALARM
  • PromQL alarm checkout-error-rate-slo flips to ALARM
  • Hand it to the DevOps Agent:
    "give me an overview of my recent alarms"
  • Then: "investigate checkout-error-rate-slo and find the root cause"
  • Agent correlates the outcome="error" spike on checkout-service
  • Recover: ./inject-fault.sh none → back to OK
Speaker (Act 4, ~18m — the payoff): Run the healthy query FIRST so the room sees zero errors, then inject the fault and explain what it does (flips an SSM flag the app polls every 5s — no redeploy). While the ratio climbs, talk through the alarm's PromQL so the wait feels intentional. Once it's ALARM, hand to the agent and read its reasoning aloud as it works — never sit in silence. Recover at the end so you leave the system green.

Act 5 · Impact & takeaways

What you take home

Cost levers

  • Export interval — fewer points on the wire (60s prod; 15s for demo speed)
  • Control label cardinality
  • High-cardinality store: up to 150 labels/series (preview — price accordingly)

Repeatable pattern

  • OTel-native, SigV4 to monitoring.us-east-1
  • PromQL to query and alarm
  • Agent for RCA — auto-triggered if you want it

Takeaway: the whole pipeline is one repeatable pattern — OTel SDK → ADOT SigV4 → CloudWatch OTel store → PromQL to query and alarm → agent for RCA. Apply it to your own service the same way; the internal repo has the reference implementation.

Speaker (~7m, close): Land the pattern, not a product pitch — this is an internal reference, not a public giveaway. Name the preview caveat honestly (pricing and label limits can still change). Close on the reliability story: one observation, followed honestly from birth to root cause. Then open Q&A.
Backup · PromQL cheat-sheet

Exact selectors

# request rate sum(rate(checkout_requests_total[1m])) # error ratio (SLO) — inline label matcher needs the __name__ form sum(rate({__name__="checkout_requests_total", outcome="error"}[1m])) / sum(rate({__name__="checkout_requests_total"}[1m])) # alarm: … > 0.2 # p95 latency (seconds-scale buckets) histogram_quantile(0.95, sum(rate(checkout_request_duration_seconds_bucket[5m])) by (le)) # always --region us-east-1 ; short [1m] windows for live responsiveness
Speaker (backup): Only show if the terminal fails or someone asks for exact selectors — otherwise stay live. The one gotcha worth saying aloud: a bare metric name with an inline {label=} matcher is rejected by the query API — use the {__name__=...} form. Note the seconds-scale histogram buckets so p95 reads correctly.
Backup · DevOps Agent prompts

Prompt-crafting for RCA

  • "Error rate on checkout-service breached 20% at <time> — what changed?"
  • "Correlate checkout_request_duration_seconds latency with the outcome="error" spike"
  • "Which fault mode explains the /checkout errors — latency or 5xx?"

Reminder: the agent is read-only by design — it investigates, you remediate.

Speaker (backup): Use if the live agent stalls, or to teach prompt-crafting — show how naming the metric, the time, and the suspected cause steers the investigation. Lean on the read-only-by-design point; it reassures security-minded folks that the agent investigates but won't touch prod. Good spot to take a question while the room is engaged.
